# 个人风格

适用：在现成风格上改造、从空白建立视觉规则、保存并复用用户自己的风格。故事、时长和本片文案变化本身不需要新建风格。

## 定方向

优先读取用户指定位置，其次环境变量 `JT_VIDEO_STYLES_HOME`，否则用当前项目 `my-styles/README.md`。可以在用户指定的共享目录保存；不默认写用户主目录或安装到全局。没有索引时不要声称已有个人风格。

改造现成风格时先读其完整 `STYLE.md`。空白起步时根据参考与用途选择一个最接近的技术基础，说明原因，借用其他风格的技术时记录来源。

| 改动 | 决策要点 |
| --- | --- |
| 调色板、字体、速度、配器、部分标志动作 | 常可保留基本风格；检查文字对比、语言覆盖与音画联动 |
| 材质、色彩逻辑、镜头语法 | 会明显改变观感，说明取舍，并在风格帧里验证 |
| 核心表达或引擎 | 可能已经成为新风格；可以重新命名和选择技术基础，不假装仍与原风格完全相同 |

把“高级、活泼、安静”转成可见的颜色数量、空间比例、对比、运动速度和声音密度。用户要共同设计时每次聚焦 1 个问题或一组紧密相关的决策，给具体选项；已给约束或授权“你定”就直接落实，不强制十轮访谈。一次改造聚焦少量可辨别的变化，避免同时改完后无法判断原因。

## 先在项目里证明，再保存

1. 在当前测试工程的 `style/` 保存中文 `STYLE.md`、`CHANGES.md` 和 `style.json` 草案；它们属于可逆的本地设计工作，无需另设写文件审批。
2. 渲染真实风格帧。改造已有风格时，用同一构图、同一内容渲染原版与新版并排对照，避免故事差异混淆判断。用户要求审风格帧时等待反馈；已授权自主完成时自检后继续。
3. 制作约 15–30 秒测试片，把每项修改落实到可指出的时间点，并包含标志动作、音乐与拟音。配音、字幕按测试目标决定，不能为了演示强加。测试片故事独立于基础 demo。
4. 交付测试片和修改映射，按 [验收清单](quality.md) 检查。用户要求保存个人风格时保存到已选位置并更新索引；未授权持久复用时先留在当前项目，不用“个人风格已经保存”描述草案。
5. 从保存后的 `demo/` 运行重建命令，把输出指向独立临时目录；验证源码目录没有新增或改写文件。缺少必要资源时不能把这个包登记为已通过重建。

## 风格包

| 文件 | 内容 |
| --- | --- |
| `style.json` | `slug`、`cn`、`en`（适用时）、`based_on`、`borrows`、`size`、`fps`、`library_version`、`created`、`line_cn` |
| `STYLE.md` | 完整中文规则：本质、材质、色彩、排版、运动、镜头、声音、标志动作、风险、引擎和可变空间；不把演示故事写成通用限制 |
| `CHANGES.md` | 每项决定的原状、现状、原因、代价、演示时间点 |
| `DEMO.md` | 这一支示例的故事与构建方式，明确它只是示例 |
| `demo/` | 可重建源码、必要的小素材、构建入口和 CREDITS；不带 node_modules、venv、帧缓存 |
| `styleframe.jpg` | 实际风格帧；改造时另有 `styleframe-vs-base.jpg` |
| `test.mp4`、`test.jpg` | 测试成片和海报 |

slug 使用小写英文、数字和连字符，不能与已登记风格冲突；重复名称时保留现有版本，先解决命名或明确更新目标。`library_version` 写完整上游 commit，继承的 MIT 许可留在源码署名中。

以后使用个人风格时，读它的规则、示例与本地技术代码，再按需读基础库。只在用户要求升级且评估差异后更新风格，不随上游升级改动用户副本。用户针对一支片子的修改，不自动写进可复用风格。
