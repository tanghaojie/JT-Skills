# 添加与维护 Skill

## 1. 从一个重复任务开始

把原始提示词保存在 [inbox](../inbox/README.md)。提炼它要解决的问题、需要的输入、交付结果和判断好坏的标准。

同一个任务的不同措辞可以合并；交付结果不同的任务通常分开。例如「文章改写」与「文章转 PDF」分别属于写作和文档处理。

## 2. 选择主要领域

从[分类导航](../README.md#分类导航)选择目录，以主要交付结果为依据。跨领域任务先选主要领域，需要时在其他领域索引中链接，不复制实现。只有确实能够跨领域复用的独立任务才放入 shared。

## 3. 建立 Skill 文件夹

例如创建 `skills/writing/jt-article-rewrite/`，把 [SKILL.md.template](../templates/SKILL.md.template) 复制到其中并重命名为 `SKILL.md`。

- 名称使用小写英文、数字和连字符，少于 64 个字符；建议使用 `jt-` 前缀。
- 文件夹名与 YAML frontmatter 中的 `name` 完全一致，且在仓库内唯一。
- `description` 说明具体能力和触发场景，让 AI 能区分相邻 Skill。
- 替换全部占位文本，删除不适用的章节；不要直接把模板登记为可用 Skill。

例如，文章改写 Skill 可以使用以下 frontmatter；这只是命名示例，仍需根据实际提示词编写执行规则：

```yaml
---
name: jt-article-rewrite
description: "按指定读者与语气改写已有文章，保留原文事实与来源。用于已有草稿的表达和结构调整。"
---
```

## 4. 按需补充资源

最小 Skill 只需要 `SKILL.md`。有实际用途时再添加以下内容：

| 路径 | 用途 |
| --- | --- |
| `scripts/` | 需要反复执行或稳定复现的辅助程序 |
| `references/` | 较长的规则、格式说明、示例与来源记录 |
| `assets/` | 用于生成结果的模板、图片、字体等素材 |
| `agents/openai.yaml` | 目标宿主支持的展示信息及调用配置，按接入需求添加 |

在 `SKILL.md` 中链接实际使用的资源，并注明使用时机。不要为了目录齐全而创建空文件夹。引入他人提示词、代码或素材时，记录来源与适用许可；未知信息明确标为未知。

## 5. 验证并登记

检查名称、frontmatter、资源链接和未完成的占位内容。如果当前环境提供 skill-creator 的校验工具，可运行其中的 `scripts/quick_validate.py <Skill 文件夹路径>`；格式通过不代表行为已验证。

用真实任务检验交付结果是否符合预期。存在易混淆场景时，再检查该 Skill 是否会错误接管相邻任务；有辅助脚本时运行相应验证。记录实际测试范围，不把未试用的内容描述为已验证。

在所属领域 README 的「已收录 Skill」中登记，例如：

```markdown
| Skill | 用途 |
| --- | --- |
| [jt-article-rewrite](jt-article-rewrite/SKILL.md) | 按指定读者与语气改写已有文章 |
```

这条索引仅在对应 Skill 实际创建并检查后添加。然后在 inbox 原文中补充整理结果链接。

## 6. 后续迭代与接入

根据实际使用反馈调整同一个 Skill，由 Git 保留历史；确实出现不同任务时再拆分，避免为每次修改建立 `v2`、`final` 等平行目录。

分类目录是本仓库的管理方式。后续安装时，把具体 Skill 文件夹及其依赖资源作为一个完整单元，按照目标宿主当前支持的方式安装或链接。验证宿主能够识别和调用后，再记录安装完成；无需为整理源文件预先打包插件。
